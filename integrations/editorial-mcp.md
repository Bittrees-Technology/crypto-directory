# Roles-authorized editorial MCP

The four existing public read tools remain independently available through the
[public local adapter](README.md). The source implementation at
`/api/integrations/mcp` adds 14 typed authenticated tools covering the remaining
pages and workflows. It is **default-off preparation**, with no verified enrolled
actor, source connection or native identity provider installed by this change.
The root public manifest continues to advertise only the four released reads.
Do not register/activate editorial functions merely because these files exist.

The authoritative schemas, role capabilities, normalization and page matrix are
exported from `lib/directory/editorial-contract.mjs`. The browser uses the same
native listing validator, queue, permission checks and release proposals.

| Page/workflow | MCP functions | Native authority |
| --- | --- | --- |
| Home, categories, public listing details | Existing `search`, `get_listing`, `list_categories`, `read_release` | Public |
| Sign-in and current permissions | `directory.read_access` | Approved authenticated source connection |
| Submission form and own submissions | `directory.submit_project`, `directory.list_submissions` | Any signed-in source identity; MCP also needs its own enrollment/grant |
| Change/removal form and own requests | `directory.request_change`, `directory.read_editable_listing`, `directory.list_change_requests` | Same intake rule |
| Existing listing editor | `directory.propose_edit` | Editor or native wallet Admin |
| Review queue | `directory.review_submission`, `directory.review_change` | Reviewer or native wallet Admin; no self-approval |
| Automatic editorial approval | `directory.auto_review` | Explicit current Reviewer plus exact delegated action and independent evidence |
| Needs-update and process-status pages | `directory.read_workspace` | Staff; administration view additionally needs Admin |
| Request close-out | `directory.close_change_request` | Staff; closing changes no listing |
| Proposal continuation and receipts | `directory.execute_step`, `directory.read_operation` | Same owner-bound connection, original action and current native capability |

Administration coverage reads current permissions and hands off to native Roles
controls. No function assigns roles, changes registry policy, signs a Safe
transaction, merges a pull request, publishes IPNS or changes ENS contenthash.
Any signed-in browser user can submit suggestions without staff authority. This
does not create anonymous MCP write authority or make an agent inherit a human's
role merely through ownership of its key.

## Explicit setup gates

`DIRECTORY_MCP_EDITORIAL_ENABLED` must be exactly `true` and
`DIRECTORY_MCP_CONNECTIONS_JSON` must contain one unambiguous, enabled, finite-lived
connection for the supplied source bearer. Its default is `[]`. The deployment
also requires the pinned public `DIRECTORY_MCP_ROLES_DECISION_PUBLIC_KEY`.
The source reuses its existing repository App, journal secret and ecosystem role
verification keys. No key, token or real connection is generated by this code.
The signed intake journal must already exist through the approved native setup;
MCP does not bootstrap its storage branch or silently provision another store.

Each reviewed connection contains only `id`, `enabled`, `sourceTokenHash`,
`bindingDigest`, `credentialId`, `delegationId`, `principal`, `tenant`, `workspace`,
`approvedAt`, `expiresAt`, `actions`, `gatewayPublicKey`, `actorPublicKey`,
`proofMode`, `identityBindingDigest`. Its canonical `connectionBinding` digest
binds the identity mapping, keys, exact actions and expiration. There are no URL,
repository, branch, path or caller-identity overrides. Connections last at most
24 hours. Fresh delegated proofs may use `gateway-held-delegated-v1` or
`device-held-delegated-v1`; the source verifies both public signatures and the
actor key's actual credential fingerprint, never requesting/uploading its private
key. Each step still needs a fresh external proof. Execution leases and other
proof families need their own reviewed integration and are not a fallback.

The server-owned `identityProvider` is intentionally absent from the deployed
entrypoint until a real source enrollment/mapping provider is reviewed. It must
return current verified connection/principal/credential ownership, a source-bound
opaque canonical person subject, the existing CD consent's opaque source subject,
original authentication time and identity revision. The single native identity
is already legitimately known to CD from its own owner consent. No cross-app raw
email/wallet alias list is requested or accepted. The exact frozen result schema
is `SOURCE_PERSON_RESULT_SCHEMA`, with frozen `SOURCE_PERSON_REQUEST_SCHEMA` input;
unexpected alias/contact fields are rejected.

The callback receives only opaque connection bindings and the exact metadata or
execution context. Execution context binds the queued item/revision, the digest
of the normalized payload, expected head/diff, durable operation/step and original
signed authority wrapper. Raw listing details, review rationale, source bearer,
keys and contact aliases are not sent to the identity provider. The provider's
`contextDigest` must match; a metadata lookup cannot be
reused for a mutation. It must check current enrollment, ownership, revocation and
identity links without inferring them from a label, email prefix or key ownership.
The source checks its binding digest, freshness and current signed ecosystem
Roles decision itself. An approved provider may be supplied only through trusted
server composition, never an HTTP field or configurable destination URL.
Both provider and actual actor/source setup must pass live acceptance before
activation; synthetic fixtures establish no real identity or grant.
No approved generic Roles endpoint for this projection has been verified. Do not
borrow Workflow private history/owner purpose or the shared profile display fields.
Historical/native intake without verified canonical owner provenance is held for
MCP review and automatic approval; an authorized native reviewer handles it
manually. It is never assumed to belong to an unrelated person. A future native
owner-consent integration must be reviewed before it adds that provenance.

## Signed request and source checks

Use canonical `https://cd.bittrees.org/api/integrations/mcp` with a separately
approved source bearer. Cookies are rejected and no browser session is converted
into an MCP credential. Initialization and tool schemas are filtered by the
connection's exact actions and current native role.

Every `tools/call` additionally carries the canonical base64url
`x-bittrees-mcp-decision` wrapper:
`{request, signature, principalSignature, decisionEnvelope:{decision,signature}}`.
It is bounded to 16 KiB encoded / 12 KiB decoded. The original request has dual
gateway and enrolled-actor signatures; the original Roles decision is separately
verified with the pinned issuer key. All three signatures, the exact
tenant/workspace/project/resource/action, credential, delegation, request and
operation UUIDs, canonical parameters and original expiry must match.

The project is `crypto-directory`, resource is `directory:editorial`, and action
is the exact tool name. Canonical `sourceContext` additionally binds the fixed
audience, approved opaque connection ID, connection/identity digests, durable
operation, exact step and normalized selection. Normalize with
`editorialArguments` before computing the digest: native listing trim/URL/list
normalization, explicit optional-token clearing, trimmed review evidence and
canonical removal-reason order. UUIDs are canonical lowercase. Manual review
tools cannot smuggle automatic mode; `auto_review` has its own action.

The original Roles decision lasts at most five seconds. It is checked before
durable reservation, after reading/locking state, immediately before each
business mutation and before result release. The entire native capability set
must stay unchanged during a call, including queue-read authority. No new
signature or extended expiry is minted by the source. Headers
`X-Bittrees-Mcp-Request-Id`, `X-Bittrees-Mcp-Operation-Id` and
`X-Bittrees-Mcp-Decision-Digest` bind source receipts to that exact decision.

## Durable proposals, not automatic publication

An intake/review call durably reserves its request ID and immutable operation
before changing the native journal. Approved edits and acceptance decisions
prepare an immutable proposal; preparation performs no listing/branch/PR business
write. Each subsequent step needs a **new external proof** for the same durable
operation, server-owned next step, revision, expected branch head and diff digest:

1. `create_branch`: create only `directory/change-<operation UUID>` at the exact
   approved main commit, in the existing CryptoDirectory repository.
2. `write_file`: write only the approved project filename/content at its expected
   SHA, using GitHub's atomic `createCommitOnBranch` expected-head check. Preserve
   existing metadata/body; a removal proposes `rejected` and retains the file.
   Editors cannot change verification state. See [GitHub's commit mutation](https://docs.github.com/en/graphql/reference/commits#createcommitonbranch).
3. `create_pr`: verify the sole actual changed file/content/head, then open the
   existing protected release proposal. This does not approve/merge/publish it.

Stages cannot be reordered, skipped, widened or replayed. A late/failed HTTP
response after dispatch is **held/unknown**, not proof that nothing happened.
No automatic retry, rollback, replacement operation or silent new proof occurs.
A fresh `read_operation` verifies the exact actual GitHub ref/content/PR receipt
and records the reconciliation before another step can be authorized. Read
reconciliation may record audit/status facts; it sends no listing/branch/PR
business write. A late audit write confers no next-step authority. Parent action,
native role, owner mapping and source binding must still match.

Queues keep their existing per-person and total bounds. Authenticated queue tools
default to 20 results, cap at 100, and bind further pages to a stable queue snapshot
that is unaffected by replay-cache writes. Input is bounded to 32 KiB and result
data to 128,000 bytes. Each prepared document is at most 32 KiB. The existing
signed GitHub journal keeps its 1 MiB limit, 256-record native queue limits, and
64 durable MCP operation slots. Full/ambiguous journals hold work for source
administrator review. Business/audit records are not automatically deleted. Only
the expired five-second request replay cache is compacted; expired original
proofs remain cryptographically unusable.

No new database, paid API, model/embedding call, scheduled job, credential or role
grant is installed. Submitted source URLs/evidence are plain untrusted data and
are never fetched by the editorial provider. The reviewer must independently
assess the curation policy. Keep $0 additional-spending controls and the standing
exception for routine releases on existing services; do not describe releases as
free. Existing GitHub checks, independent source approval, Vercel deployment and
verified ENS/IPNS publication remain authoritative.

Run `npm run test:directory` for real source-guard tests with synthetic keys,
identities, native Roles decisions and an in-memory GitHub API. The tests exercise
both accepted and denied proofs, opaque same-person checks, role revocation,
replay, native queues,
immutable step ordering, lost/late outcomes, exact diff reconciliation and
default-off activation. Passing tests do not activate the production provider.
